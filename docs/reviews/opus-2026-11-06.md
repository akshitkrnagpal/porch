# Porch review at HEAD 8030fdb

**Verdict:** Porch is not ready for daily use, and "Portless feature parity" is not justified yet. The 69 tests pass on this checkout (27 unit, 12 CLI, 14 config, 10 integrations, 5 lifecycle, 1 network). But the most common interactive path is broken in a way none of those tests can see: every test runs without a terminal attached.

That breakage, a frozen child process, is the actual root cause of your issue 4. The `porch shop` processes are stopped right now.

## How I checked
- I read all of `cli.rs`, `proxy.rs`, `process.rs`, `state.rs`, `config.rs` and `tls.rs`, plus the hosts/service parts of `integrations.rs`. I compared them with the Portless source (`cli.ts`, `cli-utils.ts`, `config.ts`, `certs.ts`).

## P0: blocks first run or daily use

**P0-1 (confirmed): apps that touch the terminal freeze.** This covers Turbo's TUI, Vite's keyboard shortcuts and anything that calls `setRawMode`.
- **Cause:** `process::configure` (`src/process.rs:12`) puts the child in a new process group (`process_group(0)`) while it shares porch's terminal. That group is in the background, so the first terminal-mode change or read stops it (SIGTTOU/SIGTTIN). Portless doesn't hit this: Node's `detached: true` calls `setsid()`, which detaches the child from the controlling terminal entirely (`cli-utils.ts:1604-1607`, `cli.ts:4510-4517`).
- **Evidence on your machine:** the processes for `porch shop pnpm run dev` are `turbo run dev` (PIDs 25432 and 25439) and its `git rev-parse HEAD` (25440). All three are in state `T` (stopped), in group 25391, while the terminal's foreground group is 25312. offerkit's `turbo.json` has `"ui": "tui"`. The "waiting on git" observation and the 502 are both just this stop.
- **Repro in /tmp (pty via `script`):**
  - `porch ttytest sh -c 'stty raw -echo; echo X'` → `sh` and `stty` end up stopped.
  - `porch rawtest node -e "process.stdin.setRawMode(true)…"` → `node` stops. A plain `vite` dev server in a terminal would hang the same way.
- **Scope:** direct launches (`cli.rs:1254`) and the Turbo coordinator (`cli.rs:1521`).
- **Fix:** when stdin is a terminal, either call `setsid()` in `pre_exec` (Portless parity; killing the group still works because session id = group id), or hand the terminal to the child group with `tcsetpgrp` and take it back on exit.
- **Missing test:** a pty-backed acceptance case (`script`, or the `portable-pty` crate) running `stty raw` and a Node `setRawMode` child.

**P0-2 (confirmed): the default first launch can't elevate (your issue 1).**
- **Cause:** `start_proxy` probes the port, then runs only `sudo -n true` (`cli.rs:637-643`). Without cached credentials it bails with "port 443 requires privileges…". Portless runs an interactive `sudo env … proxy start` when there's a terminal (`cli.ts:3665-3700`) and prints the two options when there isn't (`cli.ts:1384-1394`).
- **Effect:** a fresh install plus `porch myapp …` fails every time unless sudo happens to be cached. Tailscale on 443 wasn't the cause: the probe binds 127.0.0.1, which only returns a permission error.
- **Fix:** with a terminal, use interactive `sudo` (without `-n`); otherwise print the two-option message.
- **Same block, `cli.rs:643`:** when sudo isn't installed, porch silently moves to port 1355 but keeps TLS and doesn't set `unprivileged`. That lands directly in P1-1 below.

## P1: serious correctness, security or UX

**P1-1 (confirmed): a non-root proxy reports a hosts-file permission failure as "HTTP 403" (your issue 2).**
- **What happens:** `request_hosts_sync` (`integrations.rs:304-352`) tries to write `/etc/hosts` directly, fails, then asks the proxy. A proxy running as your user also fails, then returns 403 `hosts_sync_failed` (`proxy.rs:251-257`). `error_for_status()` drops the response body, so you only see "HTTP 403".
- **Who hits it:** any user-owned proxy that isn't marked unprivileged — a high `--port`, the sudo-missing fallback, or `--bind`.
- **Fix:**
  - The proxy should return 409 "not root, cannot sync hosts" unless its effective user is root.
  - The client should skip the HTTP request when the proxy isn't root, and print the error body.
  - For `*.localhost`, a failed hosts sync should be a one-time hint, not a warning on every launch, since browsers already resolve `.localhost`.

**P1-2 (confirmed): Porch can silently share a port with another server (your issue 3, and also app ports).**
- **Mechanism:** proxy listeners set `SO_REUSEADDR` (`proxy.rs:638`). On macOS that lets you bind `127.0.0.1:P` while another process is listening on dual-stack `[::]:P`. The same applies to the pre-start probe (`cli.rs:624`) and app-port reservation (`cli.rs:1150`, `1160`), because Rust's `std::net::TcpListener` also sets `SO_REUSEADDR` on Unix.
- **Repro (Python, in /tmp):**
  - `[::]` dual-stack listener, then `127.0.0.1` bind with `SO_REUSEADDR` → bind succeeds.
  - Same thing without `SO_REUSEADDR` → `EADDRINUSE`.
- **Effect:** porch reports the proxy as ready while browsers that try `::1` first reach the other server (that's exactly the old-Portless 404). Reserved app ports can also already be in use by a wildcard listener, e.g. Docker.
- **Fix:**
  - Don't set `SO_REUSEADDR` on these listeners.
  - Before declaring ready, check for wildcard and IPv6 listeners on the port (try binding `[::]:P` and `0.0.0.0:P` without reuse).
  - `doctor` should report anything else listening on the proxy port.

**P1-3 (confirmed): inside a monorepo package, running `porch` inherits the root's `name`, `appPort` and `script`.**
- **Cause:** `effective_config` → `resolve_app_config(root config, root, package dir)` copies the root's top-level fields when there's no `apps` map (`config.rs:268-273`, `573-580`).
- **Probe (case C):** root `package.json` `"porch":"proj"`, then `porch` run in `apps/web` → name `proj`. The same run from the workspace root gives `web.proj`.
- **Effect:** every package resolves to the same hostname and collides. A root `appPort` would collide the same way. Portless only inherits the root's `worktree` settings (`cli.ts:3898-3917`).
- **Docs:** this contradicts the claim in `docs/feature-comparison.md` that a root workspace name doesn't rename every package.
- **Fix:** in a package directory below the root, inherit only `worktree` (plus a matching `apps` entry). Treat a root `name` as the project domain and derive `<pkg>.<project>`.

**P1-4 (confirmed): `porch.json` and the `package.json` `porch` key take precedence in opposite orders depending on the code path.**
- `load()` (`config.rs:25-41`): `porch.json` wins and the `porch` key in `package.json` is ignored.
- `effective_config` (`config.rs:581-590`): the `package.json` `porch` key wins.
- The workspace root `script` (`config.rs:650-651`) and `turbo_command` (`config.rs:1160-1166`) use `load()`.
- **Probe (case B):** root `porch.json {"script":"start"}` with `package.json "porch":{"script":"dev"}`:
  - effective config says `dev`;
  - Turbo and the workspace plans run `start`.
- **Probe (case E):** a leaf `portless.json` is silently ignored when the `porch` key exists. That's acceptable for legacy files but deserves a warning.
- **Fix:** one resolver for each directory with one documented order, used by every caller.

**P1-5 (confirmed): the local CA and per-name certificate minting are broader than a dev tool needs.**
- The CA has no name constraints and runs from 1975 to 4096 (`tls.rs:113-119`).
- `LocalResolver` mints a certificate for any name a client asks for during the TLS handshake. Requesting `www.google.com` returned a leaf with `DNS:www.google.com`.
- Leaf certificates have CN "rcgen self signed cert", no extended key usage and validity until 4096. Portless uses 1-year leaf certificates with `extendedKeyUsage=serverAuth` (`certs.ts:19`, `471`, `844`).
- Once the CA is trusted system-wide, its key (`~/.porch/ca-key.pem`, mode 0600) can impersonate any site.
- **Hypothesis (needs a real trust install to settle):** Safari or Chrome with a system-trusted CA may reject leaves without an extended key usage or with very long validity. `security verify-cert` passed when I supplied the root directly as an anchor, which isn't conclusive.
- **Fix:**
  - Only issue certificates for configured TLDs, `.local` and registered names.
  - Set extended key usage to serverAuth and give leaves about 1 year (CA ≤10 years).
  - Add name constraints if the configured TLDs allow it.

## P2

1. **Accept errors kill the whole proxy (code-confirmed).** In `proxy.rs:684`, `listener.accept()?` propagates errors such as EMFILE or ECONNABORTED. That ends the listener task, and `serve_config` returns at `:829`. Fix: log, back off and continue.
2. **`porch <name> <cmd>` at a monorepo root gives one route for many apps.** All child tasks inherit the same `PORT` (here 4048), so whichever binds first wins. Detect an explicit `turbo`/`pnpm run dev` at a workspace root and suggest bare `porch`, or a filter.
3. **Non-interactive first run fails twice.** `trust_if_needed` refuses without a terminal (`cli.rs:712`) on top of the sudo problem. Agents, IDE tasks and Turbo-launched runs all hit it. Consider auto-continuing with the generated CA plus `NODE_EXTRA_CA_CERTS` and printing a single hint.
4. **Every request reloads and parses `state.json`** and checks owner process identity (`proxy.rs:355-371`). HMR asset bursts multiply that cost. Cache it with a file-change check.
5. **`clean_needs_elevation` defaults to sudo** whenever `SYNC_HOSTS` isn't explicitly false (`cli.rs:1731`), even if Porch never wrote `/etc/hosts`. Record whether hosts were ever written.
6. **Uppercase or underscore names are rejected instead of normalized** (probe case H). `"porch":{"name":"Web.App_X"}` fails with "invalid hostname" at launch.

## Parity assessment
The protocol layer (HTTP/1.1, h2, WebSocket including extended CONNECT, SSE streaming) and route/TLD matching look solid, and the tests cover them with real sockets. Parity fails on what matters most day to day:
- **Process launching:** the terminal freeze in P0-1. Portless works here.
- **Elevation:** no interactive sudo (P0-2).
- **Config inheritance:** root fields leak into packages (P1-3).
- **Certificate profile:** P1-5.

The test suite can't catch the first two because it never runs with a terminal, and it never runs without cached sudo. The docs' "complete" framing overstates readiness.

## Highest-value missing acceptance cases
1. A pty-attached launch of a Node `setRawMode` child, a `stty raw` child, and real `turbo run dev` with `"ui":"tui"`. Assert the child isn't stopped and the URL serves.
2. A fresh state directory with a terminal and no cached sudo: assert interactive elevation (with a sudo shim that prompts). Without a terminal: assert the two-option message.
3. A port already taken by a `[::]` dual-stack listener (and by `0.0.0.0`): proxy start and app reservation must refuse or skip it.
4. Hosts sync with a user-owned proxy that isn't unprivileged: no 403 noise, and a clear message.
5. Monorepo `porch` run from `apps/web` with a root name or appPort: hostname is `web.<project>`, and two packages started in parallel don't collide.
6. A precedence matrix (`porch.json`, `porch` key in `package.json`, `portless.json`, `portless` key, root apps entry) asserted identically through `load`, `effective_config`, `launch_plans` and `turbo_command`.
7. A request for an unknown or foreign name during the TLS handshake gets no certificate. Leaf certificates have serverAuth and ≤398-day validity. Then a real trusted-CA Safari/Chrome smoke test on one machine.
8. Proxy survives an accept error (simulate by lowering the open-file limit with `ulimit -n`).
