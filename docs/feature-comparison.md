# Feature comparison with Portless

Porch is measured against [vercel-labs/portless at `49586cf`](https://github.com/vercel-labs/portless/tree/49586cfa566ffce8dcc4368f0b74fce560dced49), as of 2026-11-06. That version includes Compose, Cloudflare, MCP, worktree templates and unprivileged binding.

The table lists each feature area, how it's tested, and what the tests don't cover. Most tests run real processes and sockets on the local machine. Tests for external tools (Docker, Tailscale, ngrok, trust stores, service managers) use fake executables that record their arguments, so they confirm what Porch asks for, not that a real system accepted it.

## Differences from Portless

Porch has its own executable, state directory (`~/.porch`), service names and hosts-file markers. It reads Portless's configuration format and `PORTLESS_*` variables, and the matching `PORCH_*` variables take precedence. Its state files aren't shared with a running Portless daemon. A root workspace `name` sets the project domain instead of giving every package the same hostname, and a package's own settings always win.

Porch also adds `list --json`, shorthands for removing and listing routes, `--bind` and `--redirect-port`, and aliases that point at a URL. It serves plain HTTP on port 7462 without sudo by default. HTTPS is opt-in (`--https` or `porch setup`), stays on the same port and trusts the local CA for the current user only. Only HTTPS on port 443 (`--https --port 443`) and machine-wide trust (`porch trust --system`) ask for sudo. A busy proxy port is reported with the process holding it and, unless you chose the port, Porch moves to the next free one. When no one is at the terminal, an untrusted new CA produces an error instead of a system prompt; automated clients can load the CA directly and pass `--skip-trust`.

## Test platforms

CI builds and tests `aarch64-apple-darwin` and `x86_64-unknown-linux-gnu` natively. On `x86_64-pc-windows-msvc` it builds, lints and runs the unit and integration tests, except the `config`, `first_run`, `integrations`, `lifecycle` and `pty` suites, which run on macOS and Linux only. Real privileged trust and service installation, live Docker and tunnel providers, and physical network changes are outside automated testing. The local CA has no DNS name constraints, because the configured domains can change; Porch enforces which names it issues certificates for instead.
