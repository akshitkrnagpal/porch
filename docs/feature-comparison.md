## Deliberate compatibility choices

Porch uses its own executable, state directory (`~/.porch`), service identity, and managed hosts markers. It reads the upstream configuration shape and public `PORTLESS_*` settings; corresponding `PORCH_*` variables take precedence. State files and internal hosts-authentication protocol are Porch-owned and are not a shared on-disk format with a running Portless daemon. A root workspace name sets the project domain without renaming every package to the same hostname; leaf app overrides remain authoritative.

The CLI adds `list --json`, route removal/list aliases, explicit bind/redirect overrides, and URL upstream aliases. Plain HTTP on port 7462 without sudo is the default; HTTPS is an explicit opt-in (`--https` or `porch setup`) that stays on the same no-sudo port and trusts the local CA for the current user only. HTTPS on 443 (`--https --port 443`) and machine-wide trust (`porch trust --system`) are the only paths that ask for sudo. Busy proxy ports are reported with their owner and, unless chosen explicitly, moved to the next free port. In unattended sessions, a newly created untrusted CA produces a descriptive error rather than an OS prompt. Automated clients can load the CA directly and use `--skip-trust`.

## Verification boundaries

CI builds and tests `aarch64-apple-darwin` and `x86_64-unknown-linux-gnu` natively. `x86_64-pc-windows-msvc` is built, linted and tested natively; the `first_run`, `integrations`, `lifecycle` and `pty` suites are Unix-only so far. Real privileged trust/service installation, live Docker/tunnel providers and physical LAN transitions are outside automated testing. Existing trusted CA identity/validity is preserved; application-level issuance policy is restricted, while the root has no DNS NameConstraints.
